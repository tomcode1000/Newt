2. THE WORKER (one page, one sandbox)
------------------------------------------------------------------------
Input: a page (markdown, from the repo source if possible, else fetched
HTML -> markdown), the docs' base URL, any test keys provided.

Tools the model can call:
  run(cmd, timeout=120, background=false)   shell in the sandbox
  write_file(path, content) / read_file(path)
  wait_for_port(port, timeout)              for "start the server" steps
  fetch(url)                                changelog, release notes,
                                            PyPI JSON, library source
                                            on GitHub - read-only
  git_context(sha)                          PR diff / commit message +
                                            the Entire checkpoint behind
                                            the commit, if the repo has
                                            Entire (entire_ctx.py)
  report(verdict)                           ends the run

Loop (system prompt rules):
  1. Plan: list the page's steps in order, mark implicit ones you add.
  2. Follow each step EXACTLY as written first. Never "improve" the
     docs while following them - that would hide the break.
  3. On failure, decide whose fault:
       AGENT   I mistyped, my sandbox lacks something any reader's
               machine would have, I misread a step -> fix, retry
               (max 3 times per step)
       DOCS    the page as written cannot work -> find WHY (fetch
               changelog / release notes / source), note the version
       HUMAN   needs sign-up, phone, payment, captcha, a real account
               -> stop that step, mark, continue if possible
       GLITCH  network timeout, registry 5xx, rate limit -> back off,
               re-run the step later (not a docs fault, not a fix)
       UNSURE  none of the above is clearly true -> send NOTHING;
               flag for a person with the evidence
  4. Report.

DOCS-FAULT GATE (added 10 Oct - the anti-spam rule, the demo's core):
  A docs_broken verdict may produce a fix only if the evidence says so,
  never on the model's say-so alone. Confidence is built from checks:
    a. reproduces: the same step fails the same way in a FRESH sandbox
    b. explained: the history shows why (PR diff / changelog / Entire
       checkpoint names the renamed or removed thing)
    c. fixed: the corrected page passes a full re-run from zero
  a + b -> write the fix; a + b + c -> send it. Missing a or b ->
  UNSURE (flag, send nothing). Every gate decision is a traced span
  in neatlogs, so the trace shows WHY each fix was or wasn't sent.

Verdict (JSON):
  status:        pass | docs_broken | needs_human | agent_gave_up
  failing_step:  index + the exact text of the step
  evidence:      command, output tail, versions installed
  cause:         one sentence + source URL (changelog line, commit)
  suggested_fix: the corrected step text
  packages:      names + versions installed (feeds the watcher)
  confidence:    0-1

Guards: step and token budget per page; every command logged to the
ledger and traced; a run that hits the budget reports agent_gave_up
(never a fake pass).

2b. THE THREE MODES (BRIEF section 4)
------------------------------------------------------------------------
newt run ./docs     Local (situation 1). All pages in the folder, against
                    the code in the working tree (installed into the
                    sandbox from the local checkout).
newt pr             PR mode (situation 2, MAIN). Inputs from the Action:
                    base sha, head sha, repo. Steps:
                      1. git diff base..head -> changed files + symbols
                         (renamed/removed functions, CLI flags, env vars,
                         config keys) - model call over the diff
                      2. affected.py: docs pages that mention them
                         (grep + model check); always include README
                      3. run those pages in sandboxes against HEAD code
                      4. broken -> fixer edits the docs files -> verify
                         from zero -> push a fix commit to the PR branch
                      5. post one PR comment (pass table or fix summary,
                         with Entire checkpoint link when present)
newt nightly <url>  Live website (situation 3). sources.py reads the
                    live docs pages, runs them against LATEST releases,
                    opens a fix PR to the docs repo if one is given,
                    else writes a report with exact fixes.

Action (action/action.yml): composite action, inputs docs, mode,
anthropic key secret, neatlogs key secret. Uses GITHUB_TOKEN to comment
and push the fix commit. Docker is available on ubuntu-latest runners,
so sandboxes work in CI the same as locally.

3. THE COORDINATOR (combining results) + THE CHANGING WORLD
------------------------------------------------------------------------
  1. Load pages, write them to the ledger, start N workers in parallel
     (N=4 on this laptop; asyncio + threads for docker calls).
  2. Collect verdicts as they land.
  3. Cluster docs_broken verdicts by root cause (model call with all
     causes + evidence): "7 pages, same rename in v3.0" -> 1 cause.
  4. Disagreement check: if pages using the same API got different
     verdicts, re-run the odd one out in a fresh sandbox before
     deciding. Log the reasoning.
  5. Per cause: fixer rewrites all affected pages -> verifier runs a
     FRESH worker on each fixed page (strict mode: must pass as
     written). Only verified fixes go into the PR.
  6. One PR per repo: summary, causes, evidence, before/after output,
     pages needing a human.

Watcher (runs during the whole run):
  - Every 30 s, checks the package index for new versions of every
    package any worker installed.
  - New release -> event -> coordinator re-queues pages that use that
    package, including ones that passed. The ui shows "re-checking".

Resume:
  - Every state change written to the ledger before acting.
  - `newt resume` picks up: finished pages stay finished, running pages
    restart in a fresh sandbox, a PR already opened is never reopened.

the answer key -> recall, false alarms, verified fixes, needs_human

BASELINE + "NOT THE DOCS' FAULT" CASES (added 10 Oct - the headline number):
  Grow the bench to ~20 real docs breaks + ~20 failures that are NOT
  the docs' fault. Build most of them as seeded pages in the lumen demo
  world (fast, cheap, known answers); the real-library pages above count
  toward the 20 breaks. Non-docs cases to seed:
    - flaky local index: returns 503 on a set fraction of requests

  Score: wrong fixes sent, real breaks fixed, flagged-for-a-person.

  sent. Newt: M." Use only the numbers the run actually produces; say
  the bench size.
  If time runs short, shrink to ~10 + ~10 rather than drop it.
